# Private media cleanup scheduler

Part of #81, extended by #85's account/media lifecycle. The application owns a small service-only durable reservation queue; no extra queue service is introduced.

`GET /api/internal/community/cleanup` requires an exact bearer credential supplied by Vercel as `CRON_SECRET`. Missing/short configuration fails closed with 503; wrong/missing authorization returns401. Authentication is independent of cookies, community membership, public flags and upload flags. The token and storage keys are never returned or logged. Each authorized invocation attempts up to ten batches of up to ten backend-claimed cleanup records within its artwork-stage budget; a failed object removal retains durable work for a later invocation. An HTTP200 means the bounded maintenance pass ran, not that every queued object has been physically removed.

The dispatcher readiness follow-up adds a `notifications` result. Missing provider credentials or a missing/short fingerprint secret returns HTTP503 with `notifications_unconfigured` after the other independent stages have been attempted. Operators can distinguish configuration failure from a configured empty queue; the local backend reports notifications `disabled` and keeps HTTP200 when its other stages complete. Only safe reason enums and counts appear in the authenticated response/log. This does not prove provider availability or inbox delivery.

## Independent execution budgets — issue #95

The maintenance runner reserves separate sequential budgets: report retention5seconds, notification dispatch10seconds, artwork media15seconds, account media10seconds. Their40second total leaves20seconds inside the route's60second platform duration. Retention and notifications run before Storage deletion; failure or timeout in any one stage does not suppress the remaining attempts. The response includes safe `stages` statuses (`completed`, `deferred`, `unavailable`) and the number of completed artwork batches in `passes`. A timed-out or failed stage returns503 `maintenance_incomplete`; unconfigured dispatch remains separately classified. A completed deletion stage means processing attempts completed, not that its durable queue is empty.

Each stage owns an AbortController. Its signal reaches Supabase Auth/PostgREST/Storage native fetch, R2 DeleteObject, and the existing Resend SDK's native fetch. The runner awaits cancellation/transport settlement itself; it never returns from a Promise.race while a mutation continues in the background. Expired budgets stop subsequent claims/candidates and writes. A provider may already have accepted an aborted request: unfinished cleanup/outbox leases remain fenced for later reconciliation, and email retries retain the same event key, frozen payload and existing24hour idempotency/quarantine rules. No new send key or automatic uncertain-message resend is introduced.

The local file adapter checks the same signals between operations, but Node's filesystem unlink is not cancelable. This is an isolated-test/demo limitation; the application forbids the local backend in a Production runtime. The40second network budget is not a guarantee about a stalled OS filesystem or host scheduling.

Focused regressions cover every stage stalled, all independent attempts inside60seconds, zero overlapping or orphaned mock transports, stopped cleanup iteration without finishing unknown outcomes, Supabase/R2 signal propagation, and the actual installed Resend SDK forwarding cancellation. Parent validation records actual results separately; writing these tests is not evidence they have passed.

The daily cron still does not guarantee a retry inside the provider's safe idempotency window. Scheduler cadence/plan ownership, queue-age/uncertain monitoring, hosted failure/retry evidence and operator recovery remain launch blockers under#95. This code does not change Vercel schedules, flags, migrations or Production configuration.
