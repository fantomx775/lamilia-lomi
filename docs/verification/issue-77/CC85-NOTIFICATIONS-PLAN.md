# CC-85 notification design — pending implementation

Read-only independent task `/root/preflight_review` inspected issue85 and existing email/cron paths. This is architecture guidance, not verification or a completed feature.

Use the existing Resend client (`src/lib/email.ts`) and a service-only durable outbox. Insert one unique outbox row for an approve/reject moderation event in the same database transaction as that decision. Sending happens after commit; provider failure cannot undo a valid decision. No new email service or transport dependency is needed.

Outbox minimum: immutable event identity/type and author identity, state, attempt count, next retry, short claim lease/token, first-send window, provider message ID and bounded sanitized error code. No copied report text, reason, private media URL or storage key. Resolve the current verified recipient from Auth at dispatch; suppress deleted/unverified/withdrawn accounts and clean pending identity-bearing jobs on account deletion. Keep retention explicit and subject to owner readiness review.

Use stable Resend idempotency key `community-moderation/<event-id>` with exactly identical payload for retries. Provider keys expire24hours after first use; a still-ambiguous outcome after that window must become uncertain/manual-review, not a blind resend. DB event uniqueness persists beyond the provider window. Provider acceptance is distinct from delivery. Source: https://resend.com/docs/dashboard/emails/idempotency-keys

Important integration constraint: resolving a current recipient on every retry can change the payload after an email address/config/template change. On first send, persist an immutable payload fingerprint/recipient fingerprint and template version (not an email snapshot if avoidable); rederive/check the same payload on retries and suppress/mark uncertain if it differs. Likewise freeze canonical link/from/template semantics. Do not reuse an idempotency key with a different body or silently send a fresh key. Minimal message says approved/rejected and links to signed-in My Creations; avoid image URLs and private reasons in email.

Test atomically queued decisions, event deduplication, concurrent lease claims/fencing, actual transient failure+retry, ambiguous response recovery/horizon, recipient/account suppression and moderation remaining committed when mail fails. Ordinary tests are provider-free or use the isolated local mail capture. For a genuine provider test, Resend officially supports delivered@resend.dev and bounced@resend.dev; server-enforce test recipients and never redirect arbitrary real-user mail during a probe. Such tests prove API/provider simulation, not inbox deliverability. Source: https://resend.com/changelog/sending-test-emails

Existing `/api/cron/review-reminders` is a pre-existing stub that reports sent without sending and fails open when CRON_SECRET is absent. Do not copy its behavior into the community dispatcher. Reuse the fail-closed, strong-secret community maintenance authorization; make any necessary small shared authorization correction explicit. Existing stub behavior must not be presented as actual email evidence. Final runtime secret/scheduler/provider checks bind the real deployment without exposing credentials.
